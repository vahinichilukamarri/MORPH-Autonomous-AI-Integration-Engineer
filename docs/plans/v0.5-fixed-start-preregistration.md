# v0.5 fixed-start run: pre-registration

Written on 2026-10-08, **before any real model call of the v0.5 repair evaluation**. It adds nothing to the
experiment's design (that is `v0.5-repair-plan.md`, section 6, with amendments A1 to A15); it records what is
expected and how the result will be read, so that neither can be adjusted afterwards. A change to any
frozen value after the first real call is a new, separately labelled run.

## 1. What runs

- Phase `fixed`: L1R and L2R on the approved S1, S3 and S4 (6 units), N = 1 per unit.
- Attempt 0 is the recorded v0.4 reply, served by an injected replay (no call). Up to 3 repairs follow,
  each a real call. Worst case 18 real calls.
- Groq `openai/gpt-oss-120b`, temperature 0, low reasoning effort, at most 4,000 output tokens: the v0.4
  settings. No tuning, no retry of a unit to improve a number, failures are results.
- Frozen by golden hashes in `backend/tests/repair/test_frozen_repair.py` (repair prompts, rendered prompts,
  caps, feedback format, guard set and modes, limits, smoke script, graph version and topology) and, for
  the v0.4 side, `backend/tests/codegen/test_frozen_codegen.py`. Amendment A15 re-froze the L1 repair
  hashes before this registration; the L2 hashes and every attempt-0 hash are unchanged.

## 2. Expected results

Only one outcome is predicted:

- **L1R S3 is predicted to reach READY and then fail the oracle** ("gate-passing, incorrect"). Its
  segment-overwrite flaw (the v0.4 proposal sends `segment` on update and overwrites an existing value) has
  no runtime signal: the validator, the gate, the generated tests and the smoke test do not exercise it.

No other outcome is predicted, and no number (units reaching READY, attempts used, tokens) is predicted.
Every other result is reported as it comes, with no claim that it was expected.

## 3. Exposure tags (fixed)

| Unit | Tag | Meaning |
|---|---|---|
| L1R S1 | `PROMPT_GAP` | attempt 0 failed the UPSERT field-list rule, which the frozen L1 prompt never states (it also failed `omit_if_null`, a model failure) |
| L1R S4 | `PROMPT_GAP` | the same |
| L2R S1 | `CAUSE_CONTRADICTION` | conflict-exposed: the L2 prompt asks for `__cause__`, the gate bans dunder access. The repair prompt says to follow a check over a conflicting hint, so this unit measures **compliance** with that instruction, not discovery of the conflict |
| L1R S3 | `SECRET_LITERAL_FALSE_POSITIVE` | `SECRET_LITERAL`-exposed: the gate flags benign long identifiers in generated test data |
| L2R S3, L2R S4 | `MODEL` | model failures (a stray closing brace) |

Results are reported with all units and with the exposed ones separated; neither number replaces the other.

## 4. Interpretation rules (fixed)

1. N = 1 per unit: nothing is statistically significant, and a difference of one unit is noise.
2. READY is not success. A unit that reaches READY and fails the oracle is reported as
   **READY-but-incorrect** ("gate-passing, incorrect"), never as a repair success.
3. A unit stopped by the size guard or ended as `SIZE_REJECTED` is `INFRA_STOPPED`, reported as "not run",
   and **stays in every denominator**. It is a result about the infrastructure, not about the model.
4. A condition with fewer than 2 of its 3 units runnable is **"not measurable at this tier"**, and is
   never reported as a model result.
5. Seeded attempt-0 tokens are reported apart from the repair cost. Reasoning tokens are reported as the
   provider gives them, with the check of whether `total_tokens` includes them.
6. A pause (a rate limit or a cap) is reported and the run stops there; it is not worked around.
7. The oracle grades a READY unit once, after the loop, and its result never reaches the repair code.

## 5. Caps (fixed)

- `--max-real-calls 20` (the plan's cap for the fixed phase; the harness refuses a higher value).
- `--max-real-tokens 160000`, which is 0.8 x 200,000, where 200,000 is the daily token limit (TPD) that
  Groq's published rate-limit table lists for `openai/gpt-oss-120b` (read on 2026-10-08, the same row that
  lists 30 requests per minute, 1,000 per day and 8,000 tokens per minute; the 8,000 per minute equals the
  value seen in the v0.4 response headers). The page labels the table as the base limits of the Developer
  plan, so the daily figure for this key's free tier is **published, not observed**. If the key's real daily
  limit is lower, the provider answers 429, the run pauses, and that is reported.
- The harness counts input + output + reasoning of every real call (an upper bound that may double-count
  reasoning) and refuses a call whose own estimated size would pass the cap. A worst-case run (18 calls) may
  exceed 160,000 tokens (ESTIMATE); if it does, the run pauses at the cap, the unfinished units are reported
  as unfinished, and no cap is raised to finish them.
- The per-minute limit (8,000) is respected by the existing pacer. A unit whose request estimate exceeds
  8,800 tokens is stopped before the call (`INFRA_STOPPED`, "not run"); one the provider refuses as too
  large is `SIZE_REJECTED`.

## 6. Outputs of the run

After the run: replays exported and committed (`bench/replays/repair/fixed/`), results published with their
provenance (`bench/results/repair-v0.5/fixed/`, `post_run_edits: []`), READY units graded once by the oracle,
`docs/repair-eval.md` regenerated by `render_reports` and `docs/repair-eval-findings.md` written from it.
`render_reports --check` runs in CI and fails on any undeclared edit.
