## 4. Resolved [verify] items

### (a) Do the generated tests exercise `sync.py`? **No.**

`backend/app/codegen/generated_tests.py` renders three files. The runner imports only
`integration.transform.to_target` and `morph_runtime.ops.FieldTransformError`, and compares the
result of `to_target` on each case record with the value the DSL interpreter computes. Nothing
imports `integration.sync`, `integration.strategy` or `integration.clients`. Consequences:

- For L2 the generated tests execute **none** of the model's code. They are identical to D's.
- For L1 they execute none of the model's *strategy* either (create or update field lists,
  `omit_if_null`, `create_only`); only the edge-record inputs reach `to_target`.
- Therefore the smoke test in plan section 1.4 is the only runtime signal on the model's
  contribution, and the pre-registered L1 S3 prediction (section 6 of the plan) holds: the
  `segment` overwrite has no runtime signal in the repair loop.

**Related finding: D has no `sync.py`.** D's bundle is `clients.py`, `strategy.py`, `transform.py`
and an `__main__.py` that calls `morph_runtime.cli.main(...)`, which runs the runtime's `SyncEngine`.
Only L2 adds `integration/sync.py` (entry: `run_module(sync.run)`). The plan's statement "must pass
D's `sync.py`" was therefore rewritten: guards run on D's `integration/*.py` plus the runtime's
`morph_runtime/sync.py` as a reference, and the smoke test targets the **bundle entry point**, which
exists for D, L1 and L2.

**Smoke-test feasibility spike (not committed; run locally, temporary test removed).** A script
passed as `python -E -s -B -c <script>` to the existing `SandboxRunner` (network disabled, bundle
mounted read-only, the same limits) patched `integration.clients` with in-memory fakes, ran the
bundle's entry with `runpy`, and checked only that a JSON report with `records` and `requests`
came back. On D's bundle it passed for all three scenarios: S1 and S4 produced 13 record results,
S3 (keys mode, keys supplied through `MORPH_SOURCE_KEYS`) 16, with exit code 0 and an empty stderr.
**No sandbox containment change is needed**: the runner already accepts an arbitrary argv and mounts
only the bundle. The fake clients take their page-key names from `manifest.json`, which exists in
every bundle.

### (b) Are L1 edge-record expected values computed by the compiler or supplied by the model? **Computed by the compiler.**

`parse_edge_records` accepts a proposed record only if its keys are exactly the source fields and every
value is a scalar; the model supplies source records and nothing else. The expected output for each
record is `expected_for(...)`, which runs the DSL interpreter over the approved mappings
(`generated_tests.py`), and a record on which a mapping raises expects `{"__error__": <field>}`. So a
model cannot weaken expected values; it can only choose trivial inputs or supply fewer records (at
most `MAX_EDGE_RECORDS`).

### (d) Is a documented alternative to `__cause__` available in the runtime? **No structured one.**

`runtime_api.md` documents `FieldTransformError` with `field` and `detail` only, and
`MissingFieldError` as "the cause of a FieldTransformError when a source field is absent". The only
structured way to tell a missing source field from another transform error is
`isinstance(error.__cause__, MissingFieldError)`, which is what the prompt asks for and the gate
bans. The remaining option is matching the free-text `error.detail` (for example the phrase
`record has no field`), which works but is brittle and is not documented as a contract. The
runtime's own `SyncEngine` uses `__cause__` (`morph_runtime/sync.py`, trusted code outside the gate).
A prompt-v2 that stops asking for `__cause__` therefore needs a runtime attribute (a labelled
runtime version change) or a gate allowance; the plan records this under section 5.

### (e) Rendered repair-prompt token size per unit (ESTIMATE) against 8,000 TPM

No repair prompt exists yet, so the size is **estimated** as: the recorded v0.4 `prompt_tokens` for
that unit (exact, from the provider) + the previous-output echo + the feedback + a wrapper/history
line. Character-to-token ratios are assumptions and are shown as ranges:

- Echo, L1: the full v0.4 reply (an upper bound, since edge records are dropped from the echo) at
  2.1 to 3.7 characters per token. Echo, L2: the decoded module source at 3.8 to 4.8 characters per
  token. The v0.4 prompts measured 3.4 characters per token (L1) and 4.05 (L2) against the provider's
  counts; the output ratios could not be calibrated because it is unverified whether
  `completion_tokens` includes reasoning.
- Feedback: the lowered cap of 1,200 characters at 2.5 to 3.5 characters per token (343 to 480 tokens).
  Wrapper and history: about 700 characters (about 200 tokens).
- Output: the v0.4 `completion_tokens` for that unit; the upper bound adds the reasoning tokens in case
  they are not already included.

| Unit | Recorded prompt tokens | Echo (chars → tokens) | Estimated input | Estimated request (input + output) |
|---|---|---|---|---|
| L1 S1 | 4,080 | 2,375 → 642 to 1,131 | 5,271 to 5,897 | 6,383 to 7,464 |
| L1 S4 | 4,086 | 2,622 → 709 to 1,249 | 5,343 to 6,020 | 6,490 to 7,591 |
| L1 S3 | 4,029 | 2,742 → 741 to 1,306 | 5,319 to 6,021 | 6,494 to 7,581 |
| L2 S1 | 4,002 | 6,689 → 1,394 to 1,760 | 5,944 to 6,448 | 7,803 to 8,689 |
| L2 S4 | 4,008 | 6,954 → 1,449 to 1,830 | 6,005 to 6,524 | 7,778 to 8,562 |
| L2 S3 | 3,951 | 5,667 → 1,181 to 1,491 | 5,680 to 6,128 | 7,206 to 7,822 |

**Reading against the limit of 8,000 tokens per minute:** every estimated input is below 8,000; the
L1 requests are below 8,000 even in total; the three L2 requests are 7.2k to 8.7k in total, so the
upper end for L2 S1 and S4 is **above 8,000** if the whole request counts against a single minute
window. With the original 2,000-character feedback cap the figures would be about 230 to 320 tokens
higher. v0.4's largest request (4,086 input, `max_output_tokens` 4000) succeeded although their sum
exceeds 8,000, so admission does not obviously reserve the full output cap, but how Groq counts is
unverified. This is why the plan fixes the mitigation (lower feedback cap, bounded echo) and a
defined stop behaviour (pause, then `INFRA_STOPPED`) **before** the prompt is frozen, and does not
promise that it is enough. The v0.4 recorded headers also show that the window after the last call
had 3,069 tokens remaining after a 5,477-token call; I could not reconcile that exactly with the
call's reported tokens, so the pacer's header reading, not this estimate, decides waiting.
