# v0.6 M0 report: MCP SDK dependency spike

M0 scope: choose and install the MCP SDK, prove it resolves on Windows and Linux, round-trip a tool call in
memory and over stdio, and prove the SDK is imported only under `app/mcp_server`. **No real model call was
made**, no tag was created, no history was rewritten. CI results are in the reply that accompanies this
report. Numbers below are counts or outputs from this machine (Windows 11, Docker Desktop, Python 3.12.6,
uv 0.12.23); anything not verified is labelled.

## 1. Decision

**`mcp 2.3.0`**, declared as `mcp>=2.3.0,<3` in `backend/pyproject.toml`; the lock fixes 2.3.0. Rule from
the plan: the newest version that resolves cleanly and passes both round trips. `pyyaml>=6.0.3` is also
declared as a direct dependency (plan decision 6; already locked at 6.0.3 through another package, so the
lock gained no version change from it).

### Every SDK version tried

| Version | Resolves (Windows and Linux) | In-memory round trip | stdio round trip | Verdict |
|---|---|---|---|---|
| **2.3.0** (latest on PyPI at the time) | yes | pass | pass | **chosen** |
| 1.30.0 (last 1.x seen, 2026-09-07) | yes | pass | pass | **not rejected for any fault.** Passed everything; not selected only because the rule picks the newest, and 2.3.0 passed too. It remains the fallback if a later milestone finds a 2.x problem. |

No version was rejected for a defect. Versions between those two were not tried; older 1.x releases were
out of scope because the rule asks for the newest passing version.

## 2. Resolution evidence

Method: copies of `backend/pyproject.toml` and `uv.lock` in a scratch directory, `uv lock` with each version
added, compared with the untouched baseline lock.

| | 2.3.0 | 1.30.0 |
|---|---|---|
| `uv lock` | resolved, 111 packages (baseline 102) | resolved, 111 packages |
| Existing pins changed or removed | **none** | **none** |
| Added | `mcp`, `mcp-types`, `cffi`, `cryptography`, `pycparser`, `pyjwt`, `python-multipart`, `pywin32`, `sse-starlette` | `mcp`, `httpx-sse`, `cffi`, `cryptography`, `pycparser`, `pyjwt`, `python-multipart`, `pywin32`, `sse-starlette` |
| `uv pip check` in an installed venv | "All installed packages are compatible" | same |

* **Pin conflicts: none.** `langgraph 1.2.14`, `langchain-core 1.6.7`, `pydantic 2.13.5`, `starlette 1.7.0`,
  `httpx 0.28.1`, `httpx2 2.13.1`, `anyio 4.15.1` and `fastapi 0.142.2` are unchanged. `mcp 2.3.0` requires
  `pydantic>=2.12.0`, which 2.13.5 satisfies.
* **`pywin32` and Linux.** The lock is universal. `pywin32==312` is exported with the marker
  `sys_platform == 'win32'`. `uv pip install --dry-run` against both `x86_64-unknown-linux-gnu` and
  `x86_64-pc-windows-msvc` (Python 3.12) exited 0 for both versions, and the Linux plan contains no `pywin32`.
  The real Linux check is the CI run (reported in the reply).
* **Repository lock files changed:** `backend/uv.lock` and `bench/uv.lock` (bench depends on the backend by
  path), each +254 lines, nothing removed. No other lock file references `morph-backend`.
  `uv lock --check` passes for both, and both packages report `mcp 2.3.0` once synced.

## 3. Does 1.x differ from 2.x in the server API? Yes, substantially

Read from the installed packages (not from documentation):

| Area | 1.30.0 | 2.3.0 |
|---|---|---|
| High-level server | `mcp.server.fastmcp.FastMCP` | `mcp.server.mcpserver.MCPServer`; importing `mcp.server.fastmcp` raises `ModuleNotFoundError` with a migration message |
| Test client | `mcp.shared.memory.create_connected_server_and_client_session` plus `ClientSession` | a `Client` class (`from mcp import Client`) that takes a server, a transport, `StdioServerParameters` or a URL |
| Types | `mcp.types` | live in a separate `mcp-types` distribution (`import mcp_types`); `mcp.types` remains as a mirror of that namespace |
| Errors | `McpError` | `MCPError`, plus `MCPDeprecationWarning` |
| Constructor | host, port and HTTP settings on the server object | no HTTP settings on `MCPServer.__init__`; adds `middleware`, `resource_security`, `request_state_security`, `cache_hints`, `subscriptions` |
| Protocol negotiated in our probe | 2025-11-25 | 2026-07-28 |

Two points matter for M3: `MCPServer` accepts `middleware` (a candidate hook for the policy gateway; not
evaluated yet), and `resource_security` defaults reject path traversal, absolute paths and null bytes (this
covers MCP *resources*, which MORPH does not use, so it does not replace the `ingest_contract` checks).

**Interoperability (SDK to SDK only):** a 1.30.0 client calling a 2.3.0 stdio server worked (negotiated
2025-11-25), and a 2.3.0 client in both `legacy` and `auto` mode calling a 1.30.0 stdio server worked. This
suggests that clients built on the 1.x SDK can talk to a 2.x server. **Not verified:** any third-party MCP
client application; that is a risk carried into M3 (section 6).

### Isolation (AST plus subprocess)

1. The AST scan finds an SDK import when there is one (control on synthetic source) and finds none outside
   `app/mcp_server`; the package itself does import the SDK (positive control).
2. No module outside `app/mcp_server` imports `app.mcp_server` (the dependency direction in plan section 5),
   with a control that the helper detects such an import.
3. A subprocess imports the application's main paths (`app.main`, the D path services, repair service,
   mapping runner, discovery parser, the integrations API) and `sys.modules` contains no `mcp` or
   `mcp_types` module.
4. `import app.mcp_server` alone loads no SDK module; importing `app.mcp_server.probe` does (positive control).

## 6. Risks and notes carried forward

* **API churn.** 2.x is a new major version with a different high-level API; the code written in M3 targets
  2.x names (`MCPServer`, `Client`, `mcp_types`). If a 2.x defect appears, 1.30.0 is the tested fallback and
  would need the M3 code to use the 1.x API.
* **External clients.** SDK-to-SDK interoperability only; a real third-party client has not been tried.
* **Windows.** `pywin32 312` installs and the stdio round trip passes here. Linux behaviour of the stdio test
  is checked by CI, not locally.
* **Weight of the dependency.** The lock grew by 9 packages (`cryptography` and `cffi` among them, from
  `pyjwt[crypto]`). None of them is imported by the application outside `app/mcp_server`.
* **mypy and PyYAML.** M1 will import `yaml`; the backend needs `types-pyyaml` in its dev group then
  (bench already has it). Not done in M0 because nothing imports `yaml` yet.
* **Local environment.** `uv sync` without `--group embeddings` removes `fastembed` from a venv; I restored it
  with `--group embeddings` after the first sync. CI is unaffected.
