# v0.5 M3 report

M3 scope: the repair prompts, their freezing, the replay plumbing and the evaluation harness, plus plan
amendment A14. **No real model call was made** (the model is scripted, replayed or absent in every test),
no tag was created, no history was rewritten, and nothing was pushed until the end of the step.
Estimates are labelled **ESTIMATE**; every other number is a count from a test run on this machine
(Windows, Docker Desktop) or a recorded v0.4 value, with its evidence named. CI results are in the reply
that accompanies this report.

## 1. A14: G4 has no baseline after an unparseable attempt

- **Rule** (plan section 3, row G4): if the previous attempt's source does not parse, or its reply was
  truncated, empty or not JSON (so it has no source), G4 does not run on the next attempt; that attempt's
  own count becomes the baseline for the one after it. G4 stays reject-only and every trip is logged.
- **Code:** `type_escape_count` returns `None` for source that does not parse; `check_any_loosening` skips
  a path whose baseline is `None` (`app/repair/guards.py`). A reply with no source reaches the guard as
  `previous=None` (unchanged from M2).
- **Controls**, each a test:
  - positive: a real increase after a parseable attempt trips (`test_guards.py::test_g4_positive_control_...`,
    "rose from 1 to 5"; and the graph test `test_g4_trips_when_type_escapes_rise_between_attempts`);
  - negative: the first parseable output after an unparseable one does not trip
    (`test_g4_negative_control_first_parseable_output_after_an_unparseable_one`), and through the graph a
    full module after a stray-brace reply reaches READY (`test_a_full_module_after_an_unparseable_one_is_not_rejected_by_g4`);
  - the attempt after that is compared with the parseable one before it (`test_g4_the_attempt_after_that_...`);
  - on the **recorded v0.4 replies** (`bench/tests/test_repair_g4_recorded.py`, 4 tests): the L2 S4 and S3
    attempt-0 sources (stray `}`) do not parse and have no count; the recorded S1 module, which has escapes
    (the test asserts its count is above zero, so the negative control means something), is not rejected
    after either of them; and a real increase between parseable modules still trips.

## 2. The repair prompts (`app/repair/prompts/repair-v1/{l1_repair.md,l2_repair.md}`, `app/repair/prompts.py`)

- **Structure.** The system text is the frozen v0.4 one (it already says delimited blocks are data). The user
  text is the repair template (instructions only: the attempt number, what to do, the rules) followed by three
  delimited data blocks: `ORIGINAL_TASK` (the full v0.4 user prompt), `PREVIOUS_REPLY` and `CHECK_RESULTS`
  (the feedback with its history line). Tests assert that sentinel strings placed in the reply and the
  feedback appear only inside blocks, that data cannot close a block (`<<<`/`>>>` are neutralised exactly as in
  v0.4), and that a placeholder written inside data stays literal (one-pass substitution).
- **Caps (pre-registered).** Feedback: 8 items and 1,200 characters (`feedback.py`, M1). Previous-reply
  echo: 7,500 characters (`ECHO_CAP_CHARS`). L2 echoes the module source as plain text, not JSON-escaped; L1
  echoes the strategy with its edge records replaced by a count. Controls: a long echo is cut and says how
  much was left out; an echo within the cap is unchanged (`test_cap_positive_control_...`,
  `test_cap_negative_control_...`).
- **The replay key.** The prompt hash contains the attempt number and the feedback, so a change in either
  gives a different key (`test_the_prompt_hash_includes_the_attempt_the_feedback_and_the_previous_reply`).
- **Attempt 0 is exactly the v0.4 request** (`RepairPromptBuilder.initial` calls the frozen v0.4 builders).
  Evidence: `bench/tests/test_repair_attempt0.py` (6 tests): for S1, S4 and S3, L1 and L2, the hash the builder
  produces equals the `prompt_hash` stored with the recorded reply, and the injected replay serves that reply.
  For L1 this is the first of v0.4's two replies.
- **A design choice to know about.** The template tells the model: "if a check in CHECK_RESULTS conflicts with
  a hint in the original task, follow the check." That resolves the `__cause__` contradiction (L2 S1) in the
  checks' favour by instruction. The v0.4 gate and prompts are still frozen; this sentence is in the new repair
  prompt only. It matters when the L2 S1 result is read: the model was told how to resolve the conflict, so the
  unit measures whether it can comply with that instruction, not whether it can discover the conflict.

## 3. What is frozen before the first real call (`tests/repair/test_frozen_repair.py`, 7 tests)

SHA-256 of both prompt files; the rendered repair prompt hashes for a fixed stand-in task (L1R and L2R);
the pre-registered caps (7,500; 8, 1,200, 200 and 240 for feedback; the secret-length floor of 6); the
feedback format (one exact rendered string) and the stage order; the guard set and modes (G1–G5 enforced,
G6–G7 shadow), the no-op hash vectors and the G4 rule (a count exists only for source that parses); the limits
(3 repairs, 5 pauses) and the size policy constants (4.10 characters per token, factor 1.10, limit 8,000,

graph topology (27 edges, from `get_graph()`). The v0.4 side stays pinned by `test_frozen_codegen.py`.
A change to any value is a change to the experiment: it needs a new, labelled run and a new golden value.

## 4. The harness (`bench/morph_bench/repair_eval.py`, `bench/scripts/run_repair_eval.py`)

- **Run shape.** Conditions `L1R` and `L2R`; `--phase fixed` seeds attempt 0 from the recorded v0.4 replies
  through an injected `ReplayLLMProvider` (a missing record aborts with exit code 5 and makes no live call:
  `test_a_fixed_start_without_its_recorded_replay_aborts_and_makes_no_live_call`); `--phase fresh` makes
  attempt 0 a new call. `--scenarios S1,S3,S4` narrows a run.
- **Refusals** (`check_options`, 9 cases tested): no provider; the replay provider outside `--test-only`; a real
  provider with `--test-only`; a real provider without `--confirm-real-run`; a real run without
  `--max-real-tokens`; `--max-real-calls` above the pre-registered cap (20 fixed, 26 fresh).
- **Caps.** `BudgetedProvider` counts real calls and tokens (input + output + reasoning, an upper bound that
  may double-count reasoning) across restarts in `budget.json`, and refuses a call that would pass a cap,
  adding an estimate of the request's own size first; a completion can still overshoot by at most one
  completion. It sits inside the caching provider, so only real calls are counted (tested).
- **Pause and resume.** A cap raises `BudgetExhausted`, which is not an infrastructure failure: the harness
  exits with code 4, the unit stays unfinished, and the next start resumes the *same* run from its checkpoint
  (`runs.json` maps unit to run id). Finished units are skipped and never re-graded
  (`test_a_budget_stop_pauses_cleanly_and_the_next_start_continues_the_same_run`: the two finished attempts are
  not asked again, one run id, one result).
- **Fail-closed usage.** `ResumableProvider` now keeps `usage`, `total_tokens` and `finish_reason` through the
  store and its cache hits (it used to drop them). With `require_usage=True` a real reply without usage or
  `total_tokens` stops the run after the reply is stored. At start a real run is refused if any stored call
  lacks them (exit code 6), and a recording-path self-check runs a scripted call through the store and refuses
  if anything is lost; a test replaces the recorder with a lossy one and the self-check catches it. Evidence:
  `bench/tests/test_repair_eval.py` (28 tests).
- **One schema setup.** The harness calls `ensure_checkpoint_schema` once per start, before any session; a
  test with two units asserts exactly one call. A run against a database without the tables fails at once with
  `UndefinedTable` and makes no model call (`backend/tests/repair/test_schema_missing.py`, on a throwaway
  database, under 30 s).
- **Grading.** The harness (not `app.repair`) materialises the READY version's bundle and calls the oracle
  once; the verdict is stored on the result. A READY unit with a failing check is labelled
  "gate-passing, incorrect"; a unit that is not READY is never graded; a finished unit is not graded again
  (`test_a_ready_unit_is_graded_once_and_a_failing_oracle_...`, `..._is_never_graded`). `INFRA_STOPPED` units are
  results labelled "not run". Each unit carries the plan's exposure tag (`PROMPT_GAP`, `SECRET_LITERAL_FALSE_POSITIVE`,
  `CAUSE_CONTRADICTION`, `MODEL`). The `app.repair` isolation tests are unchanged and green (43 tests) plus a new
  check that only the prompt builder reads files, and only under its own prompt directory.
- **Provenance.** Each start writes `provenance.json` in the store (phase, git SHA, configured model id, the
  assumed per-minute token limit and where it came from, the caps, the prompt, graph and estimator versions);
  the end of the run adds the rate-limit headers actually seen. The tier is recorded, never changed.
- **Not built here, on purpose:** the report (`docs/repair-eval.md`, M4) and the development-calibration tooling.

## 5. Replay plumbing

`bench/scripts/export_repair_replays.py` turns a saved real run into `bench/replays/repair/<phase>/calls.jsonl`
(real replies keyed by prompt hash, each with usage and finish reason; no key, no header) and `expected.json`
(per unit and attempt: failed stage, output hash, feedback codes, enforced and shadow guards). It refuses results
of a test-only run. `bench/tests/test_repair_replay_plumbing.py` (4 tests) records a scripted run, exports it and
replays it offline through the harness for both phases, and the attempts match; dropping one reply makes the
replay fail loudly (exit code 5). `bench/smoke_tests/test_repair_replay.py` replays whatever is committed with the
real sandbox in the sandbox CI job. **Nothing is committed yet:** `bench/replays/repair/` holds only a README, the
parametrised replay test is skipped with that reason (the 1 skipped test below), and a second test asserts an
empty directory says why.

## 8. Things to decide or know

1. The repair prompt's "follow the check" sentence (section 2) changes how the L2 S1 result should be read.
2. L1 echoes omit the model's edge records; the model must propose them again, and a feedback item about "edge
   record 2" refers to a list it can no longer see. The feedback names the field and the length.
3. The token cap is an upper bound (reasoning may be counted twice). It can stop a run earlier than the provider's
   own count would.
4. The harness uses the configured (dev) database for real runs; the checkpointer tables are created there once
   per start. Use `--database-url` for a separate one.
5. "Fresh start needs its own approval" is a procedure, not a flag: the harness runs one phase per start, and
   starting `--phase fresh` is the act that needs your go.
