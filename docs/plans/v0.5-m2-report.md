## 3. Things the work showed

1. **The checkpointer's first `setup()` hangs behind any open transaction.** `PostgresSaver.setup()`
   builds an index with `CREATE INDEX CONCURRENTLY`, which waits for every transaction open in the
   database, including the run's own session. A run therefore never calls it. `ensure_checkpoint_schema`
   is called once at startup (a session-scoped fixture does it for the tests) and a missing schema fails
   fast. Anyone deploying this must call it before the first run.
2. **The no-op hash must count comments.** My first hash (an AST dump) ignored comments, so a repair that
   only deleted a `# noqa` looked identical to its predecessor and the run stopped as `NO_OP`. A comment is
   exactly what the suppression rule is about, so the L2 hash now ignores only blank lines and trailing
   whitespace. The plan's no-op row says so.
3. **Node order.** Guards inspect the built bundle, so the order is `validate`, `build`, `guard`, `gates`
   (the plan's diagram and table were corrected). `validate` also does the no-op check.
4. **G4 compares against the previous attempt, and that has an edge.** When the previous attempt was a
   tiny stub with no `Any` and the repair is a full module (6 `Any`), G4 trips ("rose from 0 to 6"). Real
   v0.4 modules are full modules from attempt 0, so this is not expected in the run, but G4 is a heuristic
   and a repair that grows from a stub is penalised. Decision for you: keep it as pre-registered (my
   recommendation, since it can only reject) or baseline G4 on attempt 0 instead.
5. **G5 on a path-carried id.** A first draft of the L1 test proposal, modelled on the v0.4 recorded
   ones, left `userId` out of both field lists, and G5 (correctly, by its definition) flagged it as a
   required field the request can carry. Whether the mock rejects a `PUT` body without the id is not
   established here; D includes it.
6. **A pause is an exception, not a state.** A node that hits an infrastructure failure raises `Paused`;
   the checkpoint still points at that node and `resume_repair` reruns it. The pause count is committed
   on the run row first, so it survives.

## 4. Size-estimator calibration (offline, no model; ESTIMATE)

Method: rebuild each recorded v0.4 request offline, count the characters the provider is sent (system
text, user message and the strict response schema), and compare `ceil(characters / 4.10)` with the
provider's own `prompt_tokens` from the replay fixtures. All nine recorded prompts: the six first-turn
prompts and the three re-ask prompts, which resemble repair prompts (a previous reply plus an error).
`CHARS_PER_TOKEN = 4.10` is the largest two-decimal value that under-counts none of the nine.

| Scenario | Prompt | Characters sent | Estimate (tokens) | Provider `prompt_tokens` | Difference | Error |
|---|---|---|---|---|---|---|
| S1 | L1 first turn | 17,129 | 4,178 | 4,080 | +98 | +2.4% |
| S1 | L1 re-ask | 19,459 | 4,747 | 4,701 | +46 | +1.0% |
| S1 | L2 first turn | 16,442 | 4,011 | 4,002 | +9 | +0.2% |
| S4 | L1 first turn | 17,171 | 4,189 | 4,086 | +103 | +2.5% |
| S4 | L1 re-ask | 19,501 | 4,757 | 4,706 | +51 | +1.1% |
| S4 | L2 first turn | 16,484 | 4,021 | 4,008 | +13 | +0.3% |
| S3 | L1 first turn | 16,926 | 4,129 | 4,029 | +100 | +2.5% |
| S3 | L1 re-ask | 19,186 | 4,680 | 4,661 | +19 | +0.4% |
| S3 | L2 first turn | 16,239 | 3,961 | 3,951 | +10 | +0.3% |

**Error range: +0.2% to +2.5% (mean +1.2%); no prompt is under-counted.** The characters per token of
these nine prompts range from 4.108 to 4.202, which is why one constant serves both conditions once the
schema is counted. The same table is the data of `tests/repair/test_sizing.py`.

Limits of this calibration: nine prompts from three scenarios; the repair prompts do not exist yet, and
Python source may tokenise differently from the mixed prose and JSON measured here. The re-ask rows,
which carry a previous JSON reply, are the closest available proxy and they sit at +0.4% to +1.1%. The
estimator also adds an expected completion (1,175 tokens for L1, 1,859 for L2, the largest recorded
`completion_tokens`); whether the provider counts completions against the same minute window is unverified.

**What the policy does with the repair requests (ESTIMATE, sizes from the M0 report with the mitigation
caps: feedback 1,200 characters, wrapper 700, echo as recorded):**

| Unit | Estimated repair request (input + expected completion) | Against 8,000 | Against the 8,800 hard stop |
|---|---|---|---|
| L1 S1 / S4 / S3 | about 6.4k to 6.5k | below | sent |
| L2 S1 | about 8.0k | at the limit | sent |
| L2 S4 | about 8.0k | slightly above | sent |
| L2 S3 | about 7.7k | below | sent |

Under the A11 rule none of them is stopped before a call. If the provider then answers "request too
large", the unit ends `INFRA_STOPPED` as `SIZE_REJECTED`, and a condition with fewer than 2 of 3 runnable
units is reported "not measurable at this tier". A12: attempt 0 uses the v0.4 prompts (about 4.0k input
tokens) and fits, so size risk exists only for repairs 1 to 3.
