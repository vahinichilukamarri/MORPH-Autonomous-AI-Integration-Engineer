# v0.6-mcp-policy plan

Status: approved with amendments on 2026-10-08. Plan only until each milestone is authorised; no real
model call is needed anywhere in v0.6. Estimates are labelled; counts that appear as design targets
(for example the size of the injection corpus) are fixed in the pre-registration commit of M4 and are
not results.

## 1. Decisions

1. MORPH is an MCP **server only**, over its own pipeline steps (discover, map, generate, test, repair).
   The MCP client role (consuming external MCP servers as integration targets) is cut.
2. The REST API stays outside the gateway in v0.6 (the trusted local human surface). Revisit with UI
   auth in v0.7.
3. Transport is **stdio** (plus the SDK's in-memory transport for tests). Approvals are decided on the
   REST side with an approver token (`MORPH_APPROVER_TOKEN`, environment only). Streamable HTTP is not
   in v0.6.
4. **No tool can approve, override or change policy**, and none can decide an approval, grade, or reach
   the oracle or the bench.
5. `repair_integration` is included (fresh-start semantics; at most 4 model calls per run).
6. **PyYAML is a declared direct dependency**, read with `safe_load` into a strict Pydantic model
   (`extra=forbid`). JSON is not used.
7. The audit log uses **both** an append-only database trigger and a hash chain.
8. The example client configuration is `docs/mcp/morph-client.example.json`. It is never named
   `.mcp.json`, holds no secrets and uses environment-variable references.

Goal: an agent can drive MORPH's pipeline over MCP, and nothing it does reaches a side effect without
an auditable policy decision; the v0.7 UI can show every decision, every pending approval and the
active policy.

Non-goals (cut): MORPH as an MCP client; MCP OAuth and multi-user accounts; gating REST endpoints;
policy hot-reload or any policy-editing tool; taint tracking of an external agent's context; UI work;
any claim about how external agents resist injection.

## 2. Threat model

| # | Threat | Control | Test |
|---|---|---|---|
| T1 | **Tool-call injection from observed content** (OpenAPI descriptions, field names, enum values, sample records, generated code, model replies, error text). | Decisions use only structured, server-derived inputs, never free text. Arguments are closed schemas carrying ids, not instructions. No tool can approve, change policy, grade or reach the review gate. Untrusted text in results sits in a delimited `untrusted` envelope (the existing neutralise rule). Side-effect tools need approval or a bounded budget, so a successful injection is limited to what the agent was already allowed to do. | Metamorphic test: the same call with and without a payload gets the same decision. Confused-agent test: a scripted agent that follows any instruction found in a tool result executes 0 of N forbidden actions **under our scripted adversary** (not a claim about real agents). |
| T2 | **Secret exfiltration** (model key, DB URL, sandbox mock credentials, MCP and approver tokens). | A redaction filter over every tool result, audit payload and log line, using the known secret values **and** token patterns; it fails closed. Tokens come from environment variables only. | Sentinel secrets planted, every tool called including error paths, sentinels absent from results, audit rows and captured logs. **Plus a pattern-based redaction test** (token-shaped strings that are not configured secrets). |
| T3 | **Record-data exfiltration** (tool results, model prompts, `get_integration_files`, whose generated tests embed sample values). | Tools return metadata only. File reads are filtered by the system's `data_class`. A model call on data that is not `synthetic` needs approval. Result size and record counts are capped. | A record-value sentinel with `data_class=restricted` never appears in results and its model call returns NEEDS_APPROVAL. |
| T4 | **SSRF and path escape in `ingest_contract`** (the existing ingest accepts a URL and calls `httpx.get`). | The tool accepts only a file under `spec_root`. A URL is denied by the floor unless its host is on a policy allowlist that is empty in v1. Paths are resolved and must stay inside `spec_root`. | Must-deny cases: URLs (including redirects and internal hosts), **path traversal (`..`), absolute paths, and symlinks that escape `spec_root`**. |
| T5 | **Writes to production-like targets without approval.** | Each system has policy attributes `environment` (mock, staging, production, unknown; unknown counts as production). Policy inputs come from the database, never from caller arguments. The floor denies any execute tool whose target is not `mock`. | **Verified on a synthetic target.** No real production system exists in this repository, and no claim is made beyond the synthetic one. |
| T6 | **Over-broad scopes.** | Roles `reader` and `operator`, least privilege. Per-session budgets cap model calls, sandbox runs and result bytes, **counted inside `repair_integration` too** (each model call and each sandbox run of a repair run is charged, not only the tool call). | Must-deny and must-allow lists per role. Exhausting a budget denies the next charge, including mid-repair. |
| T7 | **Confused deputy and approval abuse.** | An approval is bound to the request hash and the policy hash, is single-use and expires. Agents cannot decide approvals. | Replay, reuse, a different-arguments approval and an approval carried across a policy change are denied. Expiry tests use an **injected clock**. |
| T8 | **Policy loosening or tampering.** | See section 3. | Lock mismatch refuses to start; a floor-weakening policy is rejected at load. |
| T9 | **Audit tampering.** | Append-only by trigger and hash-chained. | UPDATE and DELETE are refused; an edited row fails chain verification; **a two-process concurrent insert test is followed by chain verification**. |
| T10 | **Gateway bypass.** | Every tool is registered through the gateway and nothing else is exposed. | A registry test over all registered tools; an AST import-direction test. |
| T11 | **Tampering with policy attributes** (`environment`, `data_class`). | `system_policy_attributes` is written **only through the approver-token REST path, audited, never through an MCP tool**. | A test enumerates every MCP tool and asserts none can write it. |

## 3. Policy design

**Format.** `backend/policy/morph-policy-v1.yaml`, parsed with `yaml.safe_load` into a strict Pydantic
model. No expression language and no code. Its canonical JSON form is hashed with SHA-256 (`policy_hash`).

**Rule vocabulary (closed).** A rule matches on tool, effect class, role, target `environment`, system
`data_class` and a few session counters. It carries `allow`, `deny` or `needs_approval`, optional limits
(`max_records`, `max_model_calls`, `max_sandbox_runs`) and a stable id and reason code.

**Evaluation.** Any matching deny wins; else any needs_approval wins; else any allow applies; else the
default is deny.

**Floor.** Rules in code that the file cannot override: execute only on `mock` targets, URL fetch denied,
no secrets in output, no tool may approve, change policy, grade or bypass the review gate, result size
cap. The loader statically rejects any policy that would allow what the floor denies.

**Never loosening at runtime.**
* The server hashes the policy file at startup and compares it with the committed `policy.lock`; a
  mismatch refuses to start. There is no reload, and no tool or route modifies policy.
* Released versions are immutable (CI compares them with `policy/versions.json`). A new version is a new
  file, a changed lock and passing tests; a version that loosens relative to the previous one must declare it.
* **Scope of the lock.** `policy.lock` lives in the repository, so it guards against accidental drift and
  against edits outside review. It does **not** guard against someone with repository write access, who
  can change the file and the lock together. That is a stated limit, not a hidden one.

**Order of evaluation.** Argument schema validation, floor, policy (allow, deny or needs-approval), the
existing service function if allowed, the service's own gates (review gate, AST gate, sandbox limits),
the output filter and redaction, then audit.

**Decision record.** Decision (ALLOW, DENY, NEEDS_APPROVAL), reason code, matching rule ids, policy
version and hash, request hash, principal, tool, effect and the canonical non-secret inputs. Re-evaluating
the recorded inputs against the recorded policy must reproduce the decision.

**Existing gates.** A policy ALLOW means "may attempt"; it skips nothing. `generate_integration` on a
mapping run with unresolved fields is still `BLOCKED_PENDING_REVIEW` whatever the approvals say, and an
approval is for the tool call and never marks a mapping approved. The policy has no vocabulary to change
sandbox limits or network; sandbox limits stay code constants and `sandbox.py` is untouched.

## 4. MCP design

**Role and transport.** Server only, stdio. The stdio principal's role comes from environment
configuration. Approvals are decided on the REST side with `MORPH_APPROVER_TOKEN`.

**Tools (13).**

Read-only: `list_systems`, `get_system`, `get_mapping_run`, `get_integration`, `get_integration_files`
(filtered by `data_class`), `get_repair_run`, `list_audit_events` (the session's own events),
`describe_policy`.

Side-effect (all routed through policy and approval):

| Tool | Effect | Default outcome |
|---|---|---|
| `ingest_contract` | local write; file under `spec_root` only, size capped | operator: allow; a URL is denied |
| `propose_mapping` | local write and a model call | allow if the system is `synthetic` and within budget, else needs approval |
| `generate_integration` | condition D: local write; L1 and L2: also a model call | same rule as `propose_mapping` for the model part |
| `run_generated_tests` | sandbox, no network; target environment must be `mock` | allow within the session budget |
| `repair_integration` | fresh-start repair run (at most 4 model calls) plus sandbox; optional `run_id` resumes | needs approval unless within budget and `synthetic` |

Deliberately **not** tools: mapping approve or override, approval decisions, anything that changes policy
or `system_policy_attributes`, grading or the oracle, the bench, raw HTTP, shell or file read.

**Needs-approval contract (documented in `docs/mcp.md`).** A tool that needs approval does not block. It
returns a self-describing response: `status: needs_approval`, the `approval_id`, the request hash, the
policy version, the expiry, and plain instructions for retrying: repeat the same call with the same
arguments plus `approval_id` after a human has decided it through the REST route. An approval is
single-use, bound to the request hash and the policy hash, and expires; a retry with different arguments,
after expiry or after a policy change is denied with a stated reason code.

**Model use.** The gateway builds the provider from settings; a tool cannot choose the model or provider.
The provider is wrapped to enforce a per-call cap and charged to the session budget, goes through the
existing recording store (so every real call is recorded), and the recorded `llm_calls` ids are linked in
the audit event payload.

**Dependency.** The official `mcp` package, version chosen by the M0 spike (section 8). It is imported
only under `app/mcp_server/`, and an AST plus subprocess `sys.modules` test enforces that. `pywin32` on
Windows and pin conflicts with `langgraph`, `langchain-core` and `pydantic` are the install risks.

**Sync and async.** The backend services are synchronous SQLAlchemy; the MCP server runs them in a
threadpool with one session per call; Docker sandbox runs are serialised by a lock.

## 5. Invariants unchanged

* Condition D is unaffected: `app/policy` and `app/mcp_server` import the services and nothing imports
  them back (an AST test enforces the direction).
* The v0.4 frozen paths (generator, gate, sandbox, validators, oracle, fixtures, replays) are untouched.
  Declared changes in v0.6: dependency and lock files, new tables in `db_models.py`, migration `0009`,
  router registration in `main.py`, new settings, the CI workflow.
* `app.repair` has no path to the oracle, `morph_bench` or the answer keys, and no MCP tool exposes
  grading; `repair_integration` runs without an oracle.
* No secrets in prompts, logs, replays, audit rows or tool outputs. Policy evaluation is deterministic
  and replayable (injected clock). Every real model call is recorded. The LangSmith tracing refusal still
  applies.

## 6. Data and persistence

Migration `0009` adds:
* `policy_versions`: version, hash, stored content.
* `audit_events`: append-only (trigger rejecting UPDATE and DELETE) and hash-chained (`prev_hash`,
  `row_hash`); sequence number, event type (CALL_RECEIVED, POLICY_DECISION, APPROVAL_REQUESTED,
  APPROVAL_DECIDED, CALL_EXECUTED, OUTPUT_REDACTED), session, principal, tool, call id, redacted payload,
  policy hash.
* `approval_requests`: mutable lifecycle (PENDING, APPROVED, DENIED, EXPIRED, CONSUMED); each change is
  mirrored as an audit event.
* `system_policy_attributes`: `environment` and `data_class` per system, in a separate table so the
  discovery tables are untouched; missing means most restrictive. Writes only through the
  approver-token REST path, audited.

REST shapes for v0.7 (no UI now): `GET /policy/active`, `GET /audit/events` (filters, cursor),
`GET /audit/verify`, `GET /approvals?status=`, `GET /approvals/{id}`, `POST /approvals/{id}/decide`
(approver token), `PUT /systems/{id}/policy-attributes` (approver token), `GET /mcp/tools`.

## 7. Eval and tests (pre-registered before any run)

No real model call is needed. Model-using tools run against a fake model and the committed v0.5 replays.

* **Corpus** in `backend/tests/policy/corpus/`: must-deny, must-allow, must-need-approval and an
  `injection/` set. Case counts are fixed in the M4 pre-registration commit.
* **Controls.** Every policy rule and every floor rule has at least one positive and one negative
  control; a meta-test fails if any rule lacks either.
* **Injection corpus** (design: 8 payload classes across 5 carriers (contract descriptions, field names and
  enums, sample record values, generated-code strings, scripted model replies), N = 40 planned): decision
  invariance with and without the payload; the scripted confused agent; redaction sentinels and
  patterns.
* **Must-deny additions.** `ingest_contract` path traversal, absolute paths and symlinks escaping
  `spec_root`; URLs; every MCP tool checked for the ability to write `system_policy_attributes`.
* **Concurrency.** A two-process concurrent audit-insert test followed by chain verification.
* **Clock.** Approval expiry tests use an injected clock.
* **Claims allowed in the report,** each with denominator: must-deny cases denied X of X; must-allow
  allowed Y of Y; must-approve flagged Z of Z; injection decision invariance N of N; forbidden actions
  executed by the scripted adversary 0 of N; chain verification detecting every row in the tamper corpus;
  the production-write control **verified on a synthetic target**.
* **Limits.** The corpus is hand-written and tests our rules. It says nothing about how an external
  agent resists injection. The report is generated and checked like the v0.5 reports.

CI: the backend job runs the policy and MCP tests and a policy-check step (lock, version immutability,

subprocess round-trip runs on Ubuntu.

changes; the D golden hashes and the v0.4 replay test are unmodified; `git log --all --format=%B | grep
-i co-authored-by` is empty; `git ls-files | grep -Ei "(^|/)(\.claude/|CLAUDE(\.local)?\.md|\.mcp\.json|\.env$)"`
is empty; ruff and mypy are clean.
